# MCP Apps cross-host contract research

Status note (2026-07-26): the final
[Coach App product and implementation specification](./coach-app-product-and-implementation-specification.md)
supersedes this note's Better Auth and client-state implementation assumptions.
The protocol and host-capability findings remain the portable evidence base.

Research date: 2026-07-17

This note records the current primary-source contract that both ChatGPT and Claude consumer chat apps support for remote MCP servers with interactive UI, so the Coach App prototype can target one remote Coach MCP Server (Streamable HTTP) plus one portable MCP Apps UI bundle. Sources are the MCP specification at modelcontextprotocol.io (current revision **2025-11-25**), the official MCP Apps extension (SEP-1865, stable revision **2026-01-26**, extension id `io.modelcontextprotocol/ui`, co-authored by Anthropic and OpenAI), the OpenAI Apps SDK documentation, and Anthropic's Claude connector and MCP Apps documentation. Claims that could not be confirmed from a primary source are marked UNCONFIRMED.

## TL;DR: the common contract the Coach App can rely on

1. **One remote server, Streamable HTTP, single HTTPS endpoint.** Both hosts connect to a public HTTPS MCP endpoint speaking the Streamable HTTP transport (POST for client messages, optional SSE streaming, optional `MCP-Session-Id`). [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [OpenAI Apps SDK MCP concepts](https://developers.openai.com/apps-sdk/concepts/mcp-server), [Claude custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
2. **One portable UI bundle via the MCP Apps extension.** Predeclared `ui://` resources with mimetype `text/html;profile=mcp-app`, linked from tools through `_meta.ui.resourceUri`, rendered in a sandboxed iframe, talking MCP JSON-RPC over `postMessage`. The `@modelcontextprotocol/ext-apps` SDK auto-detects the host (Claude's standard bridge vs ChatGPT's `window.openai` environment) so one bundle serves both. [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), [Claude cross-platform guide](https://claude.com/docs/connectors/building/mcp-apps/cross-compatibility.md), [MCP blog launch post](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)
3. **UI-initiated tool calls are standard.** The view may call `tools/call` and `resources/read` against its own server; `_meta.ui.visibility` (`["model","app"]` default) controls whether the agent, the app, or both may call each tool. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
4. **Model visibility: only `content` is safely model-visible on both hosts.** The extension defines `content` for model context, `structuredContent` for UI hydration ("not added to model context"), `_meta` never for the model. ChatGPT deviates: it puts both `structuredContent` and `content` in the transcript. Portable rule: facts the Language Layer must see go in `content`; UI hydration data goes in `structuredContent` but must be safe to show a model; UI-only bulk goes in `_meta`. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), [OpenAI Apps SDK server guide](https://developers.openai.com/apps-sdk/build/mcp-server)
5. **No portable widget-state persistence.** `window.openai.setWidgetState` is ChatGPT-only; the MCP Apps MVP defers state persistence. Portable state = in-iframe runtime state + server-side state + `ui/update-model-context` for what the model should carry forward. [Migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html)
6. **OAuth 2.1 with RFC 9728 discovery works on both hosts, but registration differs.** Both hosts run authorization-code + PKCE (S256), discover the authorization server through Protected Resource Metadata, and support CIMD; Claude supports DCR out of the box while ChatGPT treats DCR as optional and prefers CIMD. Better Auth must serve RFC 8414 metadata, advertise S256, and accept both registration paths. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [OpenAI Apps SDK auth](https://developers.openai.com/apps-sdk/build/auth), [Claude connector authentication](https://claude.com/docs/connectors/building/authentication.md)
7. **Text fallback is mandatory.** Tools "MUST return meaningful content array even when UI is available", and the server should feature-detect the client's `io.modelcontextprotocol/ui` extension capability before registering UI-enabled variants. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

## Per-topic findings

### Remote Streamable HTTP servers

The server MUST provide a single HTTP endpoint supporting POST and GET. Every client JSON-RPC message is a new POST; the server answers a request with either `application/json` or an SSE stream, and the client MUST support both. The server MAY assign an `MCP-Session-Id` at initialization; clients MUST echo it, and a 404 on a session id means "start a new session with a fresh `InitializeRequest`". Servers MUST validate the `Origin` header (403 on mismatch). SSE streams MAY be resumable via per-stream event ids and `Last-Event-ID` on a GET. Disconnection "SHOULD NOT be interpreted as the client cancelling its request"; cancellation is an explicit `CancelledNotification`. [MCP transports, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

ChatGPT: "The protocol is transport agnostic; you can host the server over Server-Sent Events or Streamable HTTP", with Streamable HTTP recommended; deployment guidance requires a stable HTTPS endpoint with "low-latency streaming responses on /mcp". [OpenAI MCP concepts](https://developers.openai.com/apps-sdk/concepts/mcp-server), [OpenAI deploy guide](https://developers.openai.com/apps-sdk/deploy), [OpenAI server build guide](https://developers.openai.com/apps-sdk/build/mcp-server) ("ChatGPT requires HTTPS")

Claude: custom connectors are available on Free (one connector), Pro, Max, Team, and Enterprise across Claude.ai web, Desktop, mobile, and Cowork; the server must be "reachable over the public internet from Anthropic's IP ranges". Claude's MCP traffic egresses from `160.79.104.0/21`, and MCP tool calls are proxied through Claude's backend rather than the user's device. [Claude custom connectors help article](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), [Claude connector authentication](https://claude.com/docs/connectors/building/authentication.md), [Claude MCP Apps troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting.md)

### UI resources

The MCP Apps extension (`io.modelcontextprotocol/ui`) requires UI resources to be predeclared server resources whose URI "MUST start with `ui://`" and whose `mimeType` "MUST be `text/html;profile=mcp-app` (other types reserved for future extensions)". Tools link to a UI via `_meta.ui.resourceUri`; the older flat `_meta["ui/resourceUri"]` form is deprecated. The view runs in a sandboxed iframe and completes a `ui/initialize` → `ui/notifications/initialized` handshake, declaring `appCapabilities` (including `availableDisplayModes`) and receiving `hostContext` (theme, styles, locale, `displayMode`, container dimensions, platform) plus `hostCapabilities`. [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

ChatGPT registers the same `text/html;profile=mcp-app` templates and treats `openai/outputTemplate` and the `text/html+skybridge` mimetype as legacy aliases for `ui.resourceUri`. [OpenAI server build guide](https://developers.openai.com/apps-sdk/build/mcp-server), [migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html) Claude renders the app as a nested sandboxed iframe on desktop/web and inside a `WKWebView` on iOS. [Claude MCP Apps troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting.md)

### UI-initiated tools

Views may send a defined subset of MCP messages to the host: `tools/call`, `resources/read`, logging, plus extension methods `ui/open-link`, `ui/message` (post into the chat), `ui/request-display-mode`, and `ui/update-model-context`. Tool access control is `_meta.ui.visibility`, defaulting to `["model","app"]`; hosts MUST exclude tools without `"model"` from the agent's tool list, `"app"`-only tools are callable only by views from the same server, and cross-server app tool calls are always blocked. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

ChatGPT supports this as `window.openai.callTool` with `_meta.ui.visibility` (legacy `openai/widgetAccessible` boolean). [OpenAI reference](https://developers.openai.com/apps-sdk/reference) Claude supports app-initiated tool calls and explicitly recommends them for on-demand data loading ("Use app-initiated tool calls to load additional data from within your widget as the user explores"). [Claude MCP Apps troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting.md)

### Model-visible vs UI-only content

The extension's tool-result contract: "`content`: Text representation for model context and text-only hosts. `structuredContent`: Structured data optimized for UI rendering (not added to model context). `_meta`: Additional metadata … not intended for model context." [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

ChatGPT diverges on `structuredContent`: "the model only sees `structuredContent` and `content`" while "`_meta` never reaches the model". [OpenAI server build guide](https://developers.openai.com/apps-sdk/build/mcp-server), [OpenAI reference](https://developers.openai.com/apps-sdk/reference) ("`structuredContent` and `content` appear in conversation transcript")

Claude's own model-visibility behavior for `structuredContent` is not stated in a primary source (UNCONFIRMED; the spec default is "not added to model context"). The portable rule is therefore asymmetric-safe: anything the host model must reason over goes in `content`; `structuredContent` hydrates the view and must be assumed model-visible on ChatGPT; `_meta` is UI-only on both. For UI-driven context (for example the Player navigating to a different Critical Moment), the standard channel is `ui/update-model-context`, which hosts MAY defer until the next user message and MAY dedupe; ChatGPT documents it as the way to make UI state model-visible. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), [OpenAI state management](https://developers.openai.com/apps-sdk/build/state-management)

### Widget state

ChatGPT-only: `window.openai.widgetState` / `setWidgetState(state)` persist a snapshot "only for the widget instance tied to a specific message"; the write is synchronous with background persistence, and widget state "is not automatically visible to the model". [OpenAI state management](https://developers.openai.com/apps-sdk/build/state-management) The official migration reference marks both as "Not available in MCP", and the MCP Apps MVP explicitly defers state persistence to future extensions. [Migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html), [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) Claude documents no widget-state persistence API; it does document instance supersession (keeping only the newest widget instance active when a tool repeats). [Claude instance supersession](https://claude.com/docs/connectors/building/mcp-apps/instance-supersession.md)

### Streaming

Transport level: any tool call may stream via SSE, including server notifications before the final response. [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) Apps level: the host MAY send `ui/notifications/tool-input-partial` "zero or more times while the agent is streaming tool arguments" before the complete `ui/notifications/tool-input`, then `ui/notifications/tool-result` (or `ui/notifications/tool-cancelled`). Because partial input is a MAY, a portable view must render correctly when only the final `tool-input`/`tool-result` arrive. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) Whether each host currently emits `tool-input-partial` is UNCONFIRMED.

### Progress

Baseline MCP: a receiver may emit `notifications/progress` against a request's `progressToken`; tokens MUST be unique, and progress MAY reset request timeout clocks. [MCP progress utility](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/progress), [MCP lifecycle timeouts](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) Neither the OpenAI Apps SDK docs nor Claude's connector docs state that their consumer surfaces request progress tokens or display progress notifications (UNCONFIRMED). ChatGPT's documented long-operation affordance is instead the `openai/toolInvocation/invoking` / `invoked` status strings (≤64 chars). [OpenAI reference](https://developers.openai.com/apps-sdk/reference) Treat progress as best-effort server hygiene, not a UX dependency.

### Cancellation

Baseline MCP: `notifications/cancelled` cancels an in-flight request; receivers SHOULD stop work; disconnection is explicitly not cancellation. The 2025-11-25 revision adds task-augmented requests with their own `tasks/cancel`. [MCP cancellation utility](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation), [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) Apps level: the host notifies the view with `ui/notifications/tool-cancelled` (with reason) when a tool call is cancelled. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) Whether ChatGPT and Claude emit `notifications/cancelled` to remote servers when a user stops generation is UNCONFIRMED; the Coach MCP Server should honor it if received but must also tolerate silent abandonment (timeouts).

### OAuth discovery and client registration

MCP 2025-11-25 baseline: the MCP server is an OAuth 2.1 resource server and "MUST implement OAuth 2.0 Protected Resource Metadata (RFC 9728)", exposed via `WWW-Authenticate: Bearer resource_metadata="…"` on 401 and/or `/.well-known/oauth-protected-resource[/path]`. The authorization server MUST serve RFC 8414 metadata or OIDC Discovery. Registration priority for clients: pre-registration → CIMD (SHOULD; advertised via `client_id_metadata_document_supported`) → DCR (MAY, "for backwards compatibility"). Clients MUST use PKCE S256 and MUST refuse to proceed if `code_challenge_methods_supported` is absent; clients MUST send the RFC 8707 `resource` parameter; servers MUST validate token audience; tokens MUST NOT appear in query strings. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

ChatGPT: authorization-code + PKCE S256; requires the PRM document (`resource` echoed through the flow and expected in the token `aud`); "DCR is not required—it's optional. ChatGPT prioritizes Client ID Metadata Documents (CIMD) when available"; redirect URI `https://chatgpt.com/connector/oauth/{callback_id}` (legacy `connector_platform_oauth_redirect`); per-tool `securitySchemes` plus `_meta["mcp/www_authenticate"]` trigger the linking UI. [OpenAI Apps SDK auth](https://developers.openai.com/apps-sdk/build/auth)

Claude: supports `oauth_dcr` and `oauth_cimd` out of the box (plus Anthropic-held credentials and static headers by arrangement); CIMD is selected only when the AS metadata advertises both `client_id_metadata_document_supported: true` and `"none"` in `token_endpoint_auth_methods_supported`, otherwise Claude falls back to DCR; PKCE S256 on every authorization request; hosted surfaces redirect to `https://claude.ai/api/mcp/auth_callback`; the 401 status is required ("Claude does not honor a `WWW-Authenticate` header on a 200 response"); only the first `authorization_servers` entry is used; scope comes from the 401 `scope` parameter, else `scopes_supported` (plus `offline_access` when advertised); token endpoint must accept form-urlencoded; refresh is reactive on 401 with proactive refresh up to five minutes before expiry; OAuth discovery/registration/token endpoints get a 10-second deadline (30 s for refresh). Pure machine-to-machine `client_credentials` is not supported — every connection requires user consent. A user adding a custom connector may optionally paste a pre-registered client id/secret. [Claude connector authentication](https://claude.com/docs/connectors/building/authentication.md), [Claude custom connectors help article](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)

### Content security policy

The extension declares CSP per UI resource in `_meta.ui.csp` with `connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`; the "Host MUST construct CSP headers based on declared domains", "MAY further restrict but MUST NOT allow undeclared domains", and applies a restrictive default (`connect-src 'none'`, self + inline scripts/styles, `img-src 'self' data:`) when `csp` is omitted. Optional `_meta.ui.domain` requests a dedicated sandbox origin; `permissions` covers camera/microphone/geolocation/clipboard-write. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

ChatGPT supports standard `ui.csp` (legacy `openai/widgetCSP` with snake_case fields and an OpenAI-only `redirect_domains`); `frameDomains` is "discouraged; triggers higher review scrutiny"; `ui.domain` is required for published apps. [OpenAI server build guide](https://developers.openai.com/apps-sdk/build/mcp-server), [OpenAI reference](https://developers.openai.com/apps-sdk/reference), [migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html) Claude's `ui.domain` value must be exactly `{first-32-hex-of-SHA-256(connector URL)}.claudemcpcontent.com`, validated against the connector URL (errors instead of rendering on mismatch), and is unavailable for local stdio connectors; browser-side requests from the widget carry `Origin: {hash}.claudemcpcontent.com`, and iOS WebKit omits `Referer`, so backends must allowlist by `Origin` (`*.claudemcpcontent.com`) with proper CORS. [Claude cross-platform guide](https://claude.com/docs/connectors/building/mcp-apps/cross-compatibility.md), [Claude MCP Apps troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting.md)

### Text fallback

Clients advertise Apps support in `initialize` under `capabilities.extensions["io.modelcontextprotocol/ui"]` (with supported `mimeTypes`); servers "SHOULD check client capabilities before registering UI-enabled tools" (SDK helper `getUiCapability`), "SHOULD provide text-only fallback behavior for all UI-enabled tools", and tools "MUST return meaningful content array even when UI is available". On a non-supporting host the tool simply behaves as a standard text tool. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

### Version negotiation

Core protocol: client sends its latest supported `protocolVersion` in `initialize`; the server MUST answer with the same version or its own latest; the client SHOULD disconnect if incompatible. Over HTTP the client MUST send `MCP-Protocol-Version` on all subsequent requests; absent the header, the server SHOULD assume `2025-03-26`; invalid versions get 400. [MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) The current protocol revision is 2025-11-25; a 2026-07-28 release candidate is announced but not current. [MCP versioning](https://modelcontextprotocol.io/specification/versioning), [RC blog post](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) The Apps extension versions independently; the stable revision is 2026-01-26. [ext-apps repo](https://github.com/modelcontextprotocol/ext-apps) The exact protocol revisions negotiated by ChatGPT and Claude clients are not published (UNCONFIRMED; OpenAI's server guide references the 2025-06-18 spec). A compliant server should accept multiple revisions and let SDK negotiation resolve it.

## Host-specific extensions usable only behind feature detection

Detection mechanisms, in order of authority:

- **Server side:** inspect `initialize` `clientCapabilities.extensions["io.modelcontextprotocol/ui"]` before registering UI-enabled tool variants (`getUiCapability` helper). [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- **View side (portable):** `app.getHostCapabilities()`, `app.getHostVersion()`, and `hostContext` fields (`availableDisplayModes`, `platform`, `theme`, style variables) from the `ui/initialize` result; the spec also directs apps to "use JS feature detection as fallback" for permissions. [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), [migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html)
- **View side (host identity):** the ext-apps SDK's `App.connect()` "auto-detects the OpenAI env" and selects the transport; presence of `window.openai` identifies ChatGPT. [Migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html), [Claude cross-platform guide](https://claude.com/docs/connectors/building/mcp-apps/cross-compatibility.md)

ChatGPT-only (never required for a core journey): `widgetState`/`setWidgetState` persistence, `requestModal`, `requestClose`, `uploadFile`/`selectFiles`/`getFileDownloadUrl`, `setOpenInAppUrl`, `openai/toolInvocation/invoking|invoked` status strings, `openai/locale`/`openai/userLocation`/`openai/userAgent` request hints, `openai/widgetSessionId`, anonymized `openai/subject|session|organization` ids, `redirect_domains` CSP field. [OpenAI reference](https://developers.openai.com/apps-sdk/reference), [migration reference](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html)

Claude-only: `{hash}.claudemcpcontent.com` `ui.domain` format, Claude style-variable transparent theming, directory-connector external-link allowlists, widget instance supersession. [Claude cross-platform guide](https://claude.com/docs/connectors/building/mcp-apps/cross-compatibility.md), [transparent theming](https://claude.com/docs/connectors/building/mcp-apps/transparent-theming.md), [external links](https://claude.com/docs/connectors/building/mcp-apps/external-links.md), [instance supersession](https://claude.com/docs/connectors/building/mcp-apps/instance-supersession.md)

Host-specific `_meta.ui.domain` values are per-host data, not per-host code: the field is standard, but its value format is host-defined, so the server must compute/serve the right value per requesting host.

## Constraints on the Coach App prototype

1. **Server shape.** One Coach MCP Server on a stable HTTPS Streamable HTTP endpoint (single `/mcp`-style path), Origin-validated, session-id tolerant (rebuild on 404), grounded by durable player-owned Game Imports rather than server session lookups — consistent with the Review Session v1 in-memory model.
2. **Fact boundary maps cleanly onto content visibility.** Rule Extraction facts and Coach Turn Context material the host Language Layer must interpret go in `content` (compact, deterministic text/JSON). Position Snapshots, board rendering data, and evidence payloads for the chess workspace go in `structuredContent` — written as if model-visible, because on ChatGPT it is. Bulky UI-only data goes in `_meta`, but on Claude keep initial tool results under ~150,000 characters or the app never hydrates; page or lazy-load evidence through app-initiated `tools/call`.
3. **No persisted widget state in the portable core.** Rendering state such as the current Critical Moment and exploration branch lives in the iframe runtime plus explicit tool calls; Player plan wording remains only in host conversation. `setWidgetState` may only add resume-after-scrollback polish on ChatGPT behind `window.openai` detection. Player-visible context changes the coach must know about go through `ui/update-model-context` and/or `ui/message`.
4. **Coach Turn semantics.** One-active-Coach-Turn steering must be implemented server-side around `notifications/cancelled` when received but must not depend on hosts sending it; the view listens for `ui/notifications/tool-cancelled` to reconcile. No UX may depend on progress notifications or partial-input streaming; `openai/toolInvocation/*` strings are ChatGPT polish only.
5. **Auth via Better Auth as AS.** Serve RFC 9728 PRM (and always return 401 + `WWW-Authenticate: Bearer resource_metadata=…` — Claude requires the 401 path), RFC 8414 metadata advertising `code_challenge_methods_supported: ["S256"]`, support **both** DCR (`registration_endpoint`) and CIMD (`client_id_metadata_document_supported: true` plus `none` in `token_endpoint_auth_methods_supported`), issue audience-bound JWTs matching the exact connector URL as `resource`/`aud` (this is the Auth Token `sub` → Player ID path), rotate refresh tokens, accept form-urlencoded token requests, and keep OAuth endpoints well under Claude's 10-second deadline. List one authorization server first — Claude ignores the rest.
6. **CSP and origins.** Declare minimal `_meta.ui.csp` (ideally empty `connectDomains` by proxying everything through MCP tool calls); if the widget fetches directly, allowlist by `Origin` including `*.claudemcpcontent.com` and never by `Referer` (iOS). Compute Claude's `ui.domain` hash from the exact connector URL, including path and trailing slash.
7. **Text fallback is the Coach Skill bridge.** Every UI-enabled tool returns a complete textual Game Review / fact payload in `content`, so a host without the Apps extension still delivers the core journey; register UI variants only when the client advertises `io.modelcontextprotocol/ui`.
8. **Build on `@modelcontextprotocol/ext-apps`** (`registerAppTool`/`registerAppResource`, `App.connect()` auto-detect) rather than `window.openai` directly; that is the documented single-codebase path on both hosts.
