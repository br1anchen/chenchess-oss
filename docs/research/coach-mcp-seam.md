Research date: 2026-07-17. Resolves [Find the Coach MCP seam in the Review Session core](#65) on the [Design and prove the cross-host Coach App](#62) map.

## TL;DR

The seam already exists and is proven at two adapters. The deterministic core's interface is the `ReviewSessionCommandExecutor` trait (`backend/src/review_session_transport.rs`): `submit(principal, admission) -> event stream`. JSONL (Coach Skill) and the web NDJSON HTTP binding are its two existing adapters, and `DeliverySurface::CoachApp` is already in the v1 wire contract with its surface-ownership rules enforced. The Coach MCP Server is a **third adapter at this same seam**, and for the staging prototype it should bind at the seam's _remote projection_ — the existing `POST /api/v1/review-session/commands` NDJSON endpoint — as a thin TypeScript MCP adapter, requiring **zero changes to the Rust core**.

## The core and its interface

`ReviewSessionProcessor` ([review_session_processor.rs](../../services/coach-engine/src/review_session_processor.rs)) is a deep module. Behind one `submit` call it holds:

- the full v1 command union (`ReviewSessionCommand`, [operations.rs](../../services/coach-engine/src/review_session_contract/operations.rs)): import, session start, position inspection, Review Moment publication, stateless Player Plan Evaluation, Alternative Move exploration, Coach Turns, cancellation;
- policy admission at deserialization (`ProcessorCommandAdmission`): text and PGN size limits, surface ownership, and command-identity consistency;
- principal→surface permission (`ProcessorPrincipal::Player` permits `Web | CoachApp`; `LocalCoach` permits `CoachSkill`);
- per-principal-class compute admission pools (`CoachAdmission`: web 4 slots/8 waiting, local 1/1);
- live-operation handles with `PublicationFence` stale-result fencing and cancellation (`LiveOperation` map) — exactly the "only live task handles" the map requires the server to keep;
- Review Engine validation of host-authored Review Moment comments, Player Plan Evaluations, and Coach Turns before publication;
- provider recording verification, engine/human-model provider seams, evidence-packet append receipts.

Everything a caller must know is the wire contract generated by [Generate the operation contract and verified provider recordings](#47) — see below. The interface is small; the leverage is the whole deterministic coaching core. Tests, web, CLI, and now MCP all cross the same seam.

## What #47 exposes

`contracts/review-session/` (generated from `backend/src/review_session_contract/`, regenerate/check via `generate_review_session_contract`):

- `review-session.schema.json` — the shared command/event vocabulary: envelopes with request/operation ids, `DeliverySurface` (`web | coachSkill | coachApp`), all commands, accepted/progress events, and every terminal outcome (completed, unavailable with reasons incl. `admissionLimit`/`queueDeadline`/`languageLayer`, cancelled, conflict, rejected with recovery).
- `commands.json` / `events.json` fixtures proving web, Coach Skill, **and Coach App** inputs share one command union with explicit surface ownership (CoachApp: `LichessUrl` and `PastedPgn` allowed, `LocalPgnFile` rejected — the app-only paste path is already modeled).
- Evaluation-only provider recordings remain outside the product wire contract.
- Matching TypeScript decoders: generated types in `frontend/src/generated/review-session/` (ts-rs), with digest-verifying async decoders; Rust and TS decode the same fixtures, and drift fails verification.

So the MCP adapter's tool payloads can be typed directly from the shared contract — no new wire vocabulary, per the contract README's rule against parallel wire commands.

## Two candidate seam placements (design-it-twice)

**A. In-process Rust MCP transport** — a `review_session_transport/mcp.rs` sibling of `web.rs`, plus a Streamable HTTP `/mcp` route in the axum app, speaking MCP via the `rmcp` SDK.

**B. Remote TypeScript MCP adapter** — a thin Node server built on `@modelcontextprotocol/sdk` + `@modelcontextprotocol/ext-apps` (`registerAppTool`/`registerAppResource`), holding the `ui://` bundle, translating each MCP tool call into one signed command `POST /api/v1/review-session/commands` and folding the NDJSON event stream into one MCP tool result.

Comparison:

| Axis                          | A: Rust in-process                                  | B: TS over NDJSON endpoint                                                                                                   |
| ----------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Core changes                  | none (new transport module)                         | **none at all**                                                                                                              |
| MCP Apps support              | hand-roll `_meta.ui.*`, CSP, host detection in Rust | first-class ext-apps SDK helpers (the documented cross-host path)                                                            |
| Centralized admission/fencing | in-process                                          | **preserved** — all commands still land in the one Review Engine process holding `CoachAdmission` and the live-operation map |
| Contract typing               | native                                              | generated TS decoders already exist                                                                                          |
| Better Auth adjacency         | JWT re-validation in Rust (exists)                  | same TS ecosystem as Better Auth/Convex; PRM + 401 discovery endpoints natural here                                          |
| Cost                          | Rust Streamable HTTP + Apps plumbing                | one extra HTTP hop, one more deployable                                                                                      |

**Recommendation: B for the staging prototype.** The deciding facts: the ext-apps SDK (host auto-detection, app tool/resource registration, portable UI bundle) is TypeScript-only guidance from both hosts; the NDJSON endpoint is already a faithful remote projection of the executor seam; and centralization survives because the TS adapter is stateless per call — sessions stay client-carried, live handles and admission stay in the single Review Engine process. Option A remains open later without moving the seam: both bind the same interface, so swapping adapters never touches coaching logic. (One adapter is a hypothetical seam; we have two, and the MCP adapter makes three — the seam is real.)

## What the TS MCP adapter owns (and the core never learns)

- MCP protocol: Streamable HTTP endpoint, session-id handling, Origin validation, version negotiation, `notifications/cancelled` → a `CancelOperation` command, best-effort `notifications/progress` relay from progress events.
- MCP Apps: `ui://` resource bundle, `_meta.ui.resourceUri`/`visibility`/CSP, host feature detection, per-host `ui.domain` values.
- Content visibility split per the [cross-host contract research](mcp-apps-cross-host-contract.md): model-facing facts in `content`, UI hydration in `structuredContent` (assume model-visible), bulk in `_meta`, honoring Claude's ~150K initial-result ceiling via app-initiated paging tool calls.
- OAuth resource-server duties (PRM, 401 + `WWW-Authenticate`), forwarding the Better Auth JWT to the backend endpoint — token audience semantics across the hop belong to [Specify the Convex with Better Auth MCP authorization contract](#64).

The Review Engine core keeps exactly what it has: deterministic operations, validation, cancellation, fences, admission. Host-authored Review Moment comments, one-shot Player Plan Evaluations, and Alternative Move Assessments still cross the same `PublishReviewMomentComment`/`EvaluatePlayerPlan`/`PublishCoachTurn` boundaries every surface uses. No coaching logic is duplicated anywhere in the adapter.

## Facts the next tickets inherit

1. **Player identity is unified across web and Coach App for free.** The endpoint derives `PlayerId` as `player:sha256(sub)` from the Auth Token `sub` ([web.rs](../../services/coach-engine/src/review_session_transport/web.rs)); the same Better Auth subject yields the same Player on both surfaces, and `ProcessorPrincipal::Player` ownership checks prevent cross-Player access to sessions and operations.
2. **Imports are server-owned across Player surfaces.** `ImportGame` returns an opaque, owner-scoped `GameImportId`; `StartReviewSession` resolves the canonical Game and Review facts from the server registry. Browser and host/iframe clients never replay a snapshot or receipt protocol.
3. **Compute policy has one implementation point.** CoachApp Players currently share the web admission pool (4/8, 2 s queue deadline) keyed by principal class in `CoachAdmission` — [Set the centralized multi-session compute policy](#66) decides whether CoachApp needs its own pool; the change is local to `admission.rs`.
4. **Surface enforcement is already dual-layer.** Envelope deserialization rejects `LocalPgnFile` for CoachApp; the processor rejects surface/principal mismatches with `AuthenticationRequired`. The MCP adapter only ever stamps `surface: coachApp`.
5. **One MCP tool call maps to one command envelope.** The NDJSON response stream for that POST carries accepted → progress\* → one terminal event; the adapter folds the terminal event into the tool result and relays progress. The actual tool set and content-visibility mapping is [Design the Coach MCP tool and validation interface](#70)'s question.
