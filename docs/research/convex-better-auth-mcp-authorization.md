# Convex + Better Auth migration and OAuth 2.1 provider for Coach MCP authorization

Status note (2026-07-28): this provider path is retired and its executable
Convex source and dependencies have been removed. The document remains
historical protocol and provenance evidence; the
[Coach App product and implementation specification](./coach-app-product-and-implementation-specification.md)
is authoritative.

Research date: 2026-07-20

This note records how the development auth deployment should migrate from `@convex-dev/auth` to the official Convex + Better Auth component and mount an OAuth 2.1 authorization server so ChatGPT and Claude can authorize one Coach MCP resource with scoped JWTs whose `sub` is the canonical Player ID, verifiable offline by both Convex and the Review Engine. Sources are the Convex + Better Auth component docs and source (`@convex-dev/better-auth` **0.12.5**, [labs.convex.dev/better-auth](https://labs.convex.dev/better-auth/), [get-convex/better-auth](https://github.com/get-convex/better-auth)), Better Auth docs and source (**better-auth 1.6.23** stable, 1.7.0-rc.1 in RC; `@better-auth/oauth-provider` **1.6.23**), Convex official docs, and the MCP host contract already established in [mcp-apps-cross-host-contract.md](./mcp-apps-cross-host-contract.md) (2026-07-17), which this note treats as fixed constraints. Claims not confirmable from a primary source are marked UNCONFIRMED.

Versions researched (npm, 2026-07-20): `@convex-dev/better-auth@0.12.5` (peers: `better-auth >=1.6.11 <1.7.0`, `convex ^1.25.0`), `better-auth@1.6.23`, `@better-auth/oauth-provider@1.6.23` (peer `better-auth ^1.6.23`), `@convex-dev/auth@0.0.94` (repo currently on ^0.0.92).

## TL;DR

1. **Migrate to the official component; no official `@convex-dev/auth` → Better Auth migration guide exists.** Convex Auth remains "in beta" with no deprecation notice or Better Auth pointer in its docs ([labs.convex.dev/auth](https://labs.convex.dev/auth)); the component's own "Migrations" section covers only component-version upgrades (0.8–0.12) ([docs nav](https://labs.convex.dev/better-auth/)). Migration is manual: Better Auth stores users/sessions in its own component tables, not the `@convex-dev/auth` tables.
2. **Better Auth runs inside the Convex deployment.** The component registers via `app.use(betterAuth)` in `convex/convex.config.ts`; `authComponent.registerRoutes(http, createAuth)` mounts the Better Auth handler as Convex HTTP actions under `https://<slug>.convex.site/api/auth/`; `auth.api.*` runs in Convex functions against a component-table adapter. [Component README](https://github.com/get-convex/better-auth), [Better Auth Convex integration](https://better-auth.com/docs/integrations/convex), [create-client.ts](https://github.com/get-convex/better-auth/blob/main/src/client/create-client.ts)
3. **Plugin mode: `@better-auth/oauth-provider` (OAuth 2.1 Provider), not the `mcp`/`oidcProvider` plugins.** Both older plugins are marked "will soon be deprecated in favor of the OAuth Provider Plugin", and their access tokens are opaque DB records validated by lookup (`getMcpSession`) or remote HTTP (`createMcpAuthClient`) — no offline JWT for the Review Engine. The OAuth Provider plugin issues **JWT access tokens when the RFC 8707-style `resource` parameter is sent** (`aud` = resource, `sub` = Better Auth user id, `scope` claim), verifiable offline via JWKS. [mcp plugin docs](https://www.better-auth.com/docs/plugins/mcp), [oidc-provider docs](https://www.better-auth.com/docs/plugins/oidc-provider), [oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider), [token.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/token.ts)
4. **One issuer, one key set, two audiences.** The component's `convex()` plugin already embeds the JWT plugin with `issuer = CONVEX_SITE_URL`, `audience: "convex"`, and **forces RS256** when Convex `auth.config.ts` uses `customJwt` ("Only RS256 is supported for custom JWT with Better Auth"). OAuth access tokens are signed by the same JWT plugin keys with `aud` = the Coach MCP resource URL. The Review Engine keeps RS256 + `iss = CONVEX_SITE_URL` + static JWKS, and changes only the accepted audience (currently hardcoded `"convex"`). [convex plugin source](https://github.com/get-convex/better-auth/blob/main/src/plugins/convex/index.ts), [auth-config.ts](https://github.com/get-convex/better-auth/blob/main/src/auth-config.ts), [metadata.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/metadata.ts)
5. **Registration: DCR yes, CIMD no (until better-auth 1.7).** The OAuth Provider plugin supports RFC 7591 DCR (`allowDynamicClientRegistration`, `allowUnauthenticatedClientRegistration`); `"none"` appears in `token_endpoint_auth_methods_supported` only when unauthenticated registration is enabled. CIMD shipped as `@better-auth/cimd` in **v1.7.0-beta.1** ([PR #9159](https://github.com/better-auth/better-auth/pull/9159), [issue #7184](https://github.com/better-auth/better-auth/issues/7184)) — outside the component's `<1.7.0` peer range, so Claude will fall back to DCR (its documented behavior) and ChatGPT must use DCR too.
6. **Schema/hosting work the prototype must do:** Local Install of the component (the OAuth Provider plugin's tables `oauthClient`/`oauthRefreshToken`/`oauthAccessToken`/`oauthConsent` are _not_ in the component's stock schema, which carries only the old `oidcProvider` tables), root `/.well-known/oauth-authorization-server` route on the Convex site URL, a consent page + login page in the Vite app, and RFC 9728 PRM served by the Coach MCP server via `oauthProviderResourceClient`/`mcpHandler`. [component schema](https://github.com/get-convex/better-auth/blob/main/src/component/schema.ts), [oauth-provider schema](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/schema.ts), [Local Install](https://labs.convex.dev/better-auth/local-install), [mcp.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/mcp.ts)

## Per-topic findings

### Migration path: @convex-dev/auth → Convex + Better Auth

**Status of the two libraries.** Convex Auth is still labeled "Convex Auth is in beta" ([labs.convex.dev/auth](https://labs.convex.dev/auth)); Convex's auth overview recommends third-party auth platforms and does not mention Better Auth on that page ([docs.convex.dev/auth](https://docs.convex.dev/auth)). The Convex + Better Auth component is Convex-maintained at [github.com/get-convex/better-auth](https://github.com/get-convex/better-auth) with docs at [labs.convex.dev/better-auth](https://labs.convex.dev/better-auth/). Better Auth's own docs carry an official Convex integration page and note the component is "maintained by Convex", recommending the local-folder (Local Install) setup "to unlock the full potential of Better Auth" ([better-auth.com/docs/integrations/convex](https://better-auth.com/docs/integrations/convex)).

**No official cross-library migration guide.** The component docs' Migrations section contains only component-version guides (0.8, 0.9, 0.10, 0.11, 0.12) ([docs nav](https://labs.convex.dev/better-auth/)); Convex Auth's docs don't reference Better Auth at all. Migration is therefore manual:

- **Tables.** The component owns its schema inside the component namespace: `user`, `session`, `account`, `verification`, `twoFactor`, `oauthApplication`, `oauthAccessToken`, `oauthConsent`, `jwks`, `rateLimit` ([src/component/schema.ts](https://github.com/get-convex/better-auth/blob/main/src/component/schema.ts)). Existing `@convex-dev/auth` tables (`users`, `authAccounts`, `authSessions`, …) are untouched and unused; ChenChess must copy Players across (a one-time Convex migration writing via `auth.api` or the component adapter) or start fresh in dev.
- **Passwords.** `@convex-dev/auth`'s Password provider hashes with "Scrypt from Lucia" ([Password.ts](https://github.com/get-convex/convex-auth/blob/main/src/providers/Password.ts)); Better Auth also "uses `scrypt` to hash passwords" ([email-password docs](https://better-auth.com/docs/authentication/email-password)). Whether the stored hash formats/parameters are wire-compatible is UNCONFIRMED — Better Auth allows custom `password.hash`/`verify` to bridge, or dev test accounts can simply be recreated.
- **Player ID semantics change.** Today's `@convex-dev/auth` JWT `sub` is a composite `userId|sessionId` (`identity.subject.split(TOKEN_SUB_CLAIM_DIVIDER)` in [sessions.ts](https://github.com/get-convex/convex-auth/blob/main/src/server/implementation/sessions.ts)), so the Review Engine's "Player ID" is currently per-session. After migration, `sub` is the stable Better Auth user id (JWT plugin default: "subject claim … defaults to user ID", [jwt docs](https://www.better-auth.com/docs/plugins/jwt)) — the stable-Player-ID contract ADR 0002 wants, but any backend data keyed by the old composite sub will not match.

**How the component mounts** (from the official React/Vite example, [examples/react/convex](https://github.com/get-convex/better-auth/tree/main/examples/react/convex)):

- `convex/convex.config.ts`: `app.use(betterAuth)` with `import betterAuth from "@convex-dev/better-auth/convex.config"`.
- `convex/auth.ts`: `export const authComponent = createClient<DataModel>(components.betterAuth)`; `createAuth = (ctx) => betterAuth({ baseURL: process.env.CONVEX_SITE_URL, trustedOrigins: [siteUrl], database: authComponent.adapter(ctx), emailAndPassword: { enabled: true, … }, plugins: [crossDomain({ siteUrl }), convex({ authConfig })] })`.
- `convex/http.ts`: `authComponent.registerRoutes(http, createAuth, { cors: true })` — mounts the Better Auth handler at `pathPrefix "/api/auth/"` (GET+POST) as Convex HTTP actions, plus a root `/.well-known/openid-configuration` route that **redirects** to `/api/auth/convex/.well-known/openid-configuration` ([create-client.ts](https://github.com/get-convex/better-auth/blob/main/src/client/create-client.ts)).
- `convex/auth.config.ts`: `providers: [getAuthConfigProvider()]` which emits `{ type: "customJwt", issuer: CONVEX_SITE_URL, applicationID: "convex", algorithm: "RS256", jwks: <CONVEX_SITE_URL>/api/auth/convex/jwks }` — or a `data:` URI static JWKS when a `JWKS` env var is supplied ([src/auth-config.ts](https://github.com/get-convex/better-auth/blob/main/src/auth-config.ts)). This replaces ChenChess's current OIDC-style `{ domain: CONVEX_SITE_URL, applicationID: "convex" }` entry. Convex's `customJwt` validation requires exact `iss` match, fetched (or inline) JWKS, RS256/ES256 only, and `applicationID` matched against `aud` ([Convex custom JWT docs](https://docs.convex.dev/auth/advanced/custom-jwt)).
- Env: `npx convex env set BETTER_AUTH_SECRET=…`, `npx convex env set SITE_URL http://localhost:5173`; frontend gets `VITE_CONVEX_SITE_URL` (the `.convex.site` URL, "same as VITE_CONVEX_URL but ends in .site") and wires `createAuthClient({ baseURL: VITE_CONVEX_SITE_URL, plugins: [convexClient(), crossDomainClient()] })` + `ConvexBetterAuthProvider` ([React framework guide](https://github.com/get-convex/better-auth/blob/main/docs/content/docs/framework-guides/react.mdx)). "Since the Better Auth instance runs on Convex, environment variables used by the auth instance should be configured through the Convex CLI or dashboard" ([Convex integration docs](https://better-auth.com/docs/integrations/convex)).

**`CONVEX_SITE_URL` implications.** All Better Auth HTTP surface — sign-in, OAuth endpoints, JWKS, well-known — lives on the dev deployment's public HTTPS `*.convex.site` origin (locally `http://127.0.0.1:3211` for `convex dev` local deployments, per the React guide). That satisfies Claude's public-reachability requirement for the authorization server without any extra hosting.

### Plugin mode: which Better Auth plugin is the AS

Three candidates exist in the researched versions:

| Plugin                           | Status                                                                                                                                                      | Access tokens                                                                                                                                                                       | Fit                                                                                                                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mcp` (in `better-auth/plugins`) | "will soon be deprecated in favor of the OAuth Provider Plugin"; "based on OIDC Provider plugin" ([mcp docs](https://www.better-auth.com/docs/plugins/mcp)) | Opaque DB records; validate via `withMcpAuth`/`auth.api.getMcpSession` (same process) or `createMcpAuthClient` (per-request HTTP to Better Auth)                                    | Serves `/api/auth/.well-known/oauth-authorization-server` + `oauth-protected-resource` and its tables already exist in the component schema, but **cannot give the Review Engine offline JWT validation** |
| `oidcProvider`                   | "will soon be deprecated in favor of the OAuth Provider Plugin" ([oidc-provider docs](https://www.better-auth.com/docs/plugins/oidc-provider))              | Opaque (`oauthAccessToken` table); `useJWTPlugin` signs only **ID tokens**                                                                                                          | Same limitation                                                                                                                                                                                           |
| `@better-auth/oauth-provider`    | Current OAuth 2.1 provider; the consolidation target ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider))                       | **JWT access tokens when `resource` is requested** ("JWT Signing: sign JWT tokens when requesting a `resource`"; "JWKS Verifiable: verify tokens remotely at the `/jwks` endpoint") | Chosen mode                                                                                                                                                                                               |

`@better-auth/oauth-provider@1.6.23` peers on `better-auth ^1.6.23`, inside the component's supported `>=1.6.11 <1.7.0` range (npm, 2026-07-20).

**Endpoints exposed** (all relative to the Better Auth base, i.e. `https://<slug>.convex.site/api/auth` on Convex): `/oauth2/authorize`, `/oauth2/token` (authorization_code, client_credentials, refresh_token), `/oauth2/register` (RFC 7591), `/oauth2/consent`, `/oauth2/continue`, `/oauth2/introspect` (RFC 7662), `/oauth2/revoke` (RFC 7009), `/oauth2/userinfo`, `/oauth2/end-session`, `/jwks` (via JWT plugin), and well-known metadata ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider)). Metadata advertises `code_challenge_methods_supported: ["S256"]` only, `response_types_supported: ["code"]`, `authorization_response_iss_parameter_supported: true`, `grant_types_supported: ["authorization_code","client_credentials","refresh_token"]`, and `token_endpoint_auth_methods_supported: ["client_secret_basic","client_secret_post"]` with `"none"` prepended **only when `allowUnauthenticatedClientRegistration` is set** ([metadata.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/metadata.ts)). PKCE plain is rejected; per-client `require_pkce` opt-out exists for confidential clients ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider)). Token endpoint rate limit defaults: `/oauth2/token` 20 req/min, `/oauth2/register` 5 req/min (same docs) — fine under Claude's 10 s deadline but worth knowing for test loops.

**Well-known serving is issuer-path based.** The plugin's `onRequest` hook answers `/.well-known/oauth-authorization-server{issuerPath}` and `{issuerPath}/.well-known/oauth-authorization-server` (and `{issuerPath}/.well-known/openid-configuration` when `openid` scope is enabled), where `issuerPath` derives from the JWT plugin issuer ([oauth.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/oauth.ts)). With issuer `= CONVEX_SITE_URL` (an origin, no path), the metadata path is the **domain root** — but the component only routes `/api/auth/*` to the handler, so `convex/http.ts` must add explicit root routes (see topology below). The plugin even warns at init until the root metadata URL resolves ("Please ensure '/.well-known/oauth-authorization-server…' exists", silenced via `silenceWarnings.oauthAuthServerConfig`).

**PRM is the resource server's job.** The AS plugin does not serve RFC 9728 PRM for external resources; the companion `oauthProviderResourceClient` plugin gives the Coach MCP server `getProtectedResourceMetadata()` (fields: `resource`, `authorization_servers`, `scopes_supported`; the code notes servers "provide the `/.well-known/oauth-protected-resource` themselves") and `mcpHandler`, which wraps a request handler with Bearer extraction, `verifyAccessToken`, and on 401 emits `WWW-Authenticate: Bearer resource_metadata="{origin}/.well-known/oauth-protected-resource{resourcePath}"` — exactly the 401 path Claude requires ([client-resource.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/client-resource.ts), [mcp.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/mcp.ts)). For a Rust Coach MCP server these are just document/response shapes to replicate.

**Consent flow.** `consentPage` is a required option; `loginPage` too. `/oauth2/authorize` redirects an unauthenticated browser to `loginPage` and a consenting user to `consentPage`, carrying the original authorization query re-serialized plus `exp`, issued-at, and an integrity `sig` (signed query) ([authorize.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/authorize.ts)). The app's consent page (a route in the Vite SPA) renders client + scopes and POSTs acceptance to `/oauth2/consent`; grants persist in `oauthConsent`, and clients with `skipConsent` bypass the screen ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider), [schema.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/schema.ts)). On success the browser is redirected to the host callback (`https://claude.ai/api/mcp/auth_callback` / `https://chatgpt.com/connector/oauth/{callback_id}`) with `code`, `state`, and `iss`.

**Schema consequence → Local Install.** The OAuth Provider plugin's tables are `oauthClient`, `oauthRefreshToken`, `oauthAccessToken`, `oauthConsent` ([schema.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/schema.ts)) — different from the old `oauthApplication`/`oauthAccessToken`/`oauthConsent` trio baked into the component's stock schema ([component schema.ts](https://github.com/get-convex/better-auth/blob/main/src/component/schema.ts)). The component's supported-plugins list (Anonymous, Email OTP, Generic OAuth, JWT, Magic Link, One Tap, Phone Number, Two Factor, Username) works "without any required schema changes"; "For plugins that require schema changes and aren't in the list, check out Local Install" ([supported plugins](https://labs.convex.dev/better-auth/supported-plugins)). Local Install moves the component into `convex/betterAuth/` with a Better Auth CLI schema-generation step and "makes it possible to use plugins beyond those supported" ([Local Install](https://labs.convex.dev/better-auth/local-install)); only the SSO plugin is called out as incompatible even under Local Install. So the prototype runs Local Install and generates the `oauthClient`/`oauthRefreshToken`/… tables. Note the component's own `convex()` plugin already instantiates an internal `oidcProvider` (metadata only) and `jwt` plugin ([convex plugin source](https://github.com/get-convex/better-auth/blob/main/src/plugins/convex/index.ts)); coexistence with `oauthProvider()` in the same `plugins: []` array is not documented anywhere — a primary prototype risk (see UNCONFIRMED).

### JWT contract for Review Engine (and Convex) validation

- **Algorithm/keys.** JWT plugin default is "EdDSA with the Ed25519 curve", RS256 configurable ([jwt docs](https://www.better-auth.com/docs/plugins/jwt)), but the component forces the question: with a `customJwt` Convex auth config it throws unless RS256 (`"Only RS256 is supported for custom JWT with Better Auth"`) and sets `jwks.keyPairConfig.alg` accordingly ([convex plugin source](https://github.com/get-convex/better-auth/blob/main/src/plugins/convex/index.ts)). Convex itself supports only RS256/ES256 for `customJwt` ([Convex custom JWT docs](https://docs.convex.dev/auth/advanced/custom-jwt)). Keys live in the component `jwks` table; rotation via `auth.api.rotateKeys()`.
- **JWKS endpoints.** Two aliases of the same key set: `/api/auth/convex/jwks` (component endpoint referenced by `getAuthConfigProvider`) and the JWT plugin path used in OAuth metadata, `${baseURL}/jwks` → `/api/auth/jwks` ([auth-config.ts](https://github.com/get-convex/better-auth/blob/main/src/auth-config.ts), [metadata.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/metadata.ts)).
- **Convex session JWT** (browser → Convex, and today browser → Review Engine): `iss = CONVEX_SITE_URL`, `aud = "convex"`, 15-minute default expiry, payload = user fields (minus id/image) + `sessionId`, `sub` = Better Auth user id ([convex plugin source](https://github.com/get-convex/better-auth/blob/main/src/plugins/convex/index.ts); JWT plugin `getSubject` "defaults to user ID", [jwt docs](https://www.better-auth.com/docs/plugins/jwt)).
- **OAuth access token JWT** (hosts → Coach MCP): issued at `/oauth2/token` when the client sends `resource`; claims set explicitly: `sub = user.id`, `aud` = the requested resource (string, or array collapsed to string when single), `scope` = space-joined granted scopes; `aud` is validated against `validAudiences` (default: the Better Auth baseURL) so the Coach MCP resource URL must be listed in `validAudiences` ([token.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/token.ts) — `checkResource`: "requested resource invalid" otherwise). `accessTokenExpiresIn` default 1 h ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider)). Issuer = JWT plugin issuer (else baseURL) ([metadata.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/metadata.ts)) — with the component's convex plugin present that is `CONVEX_SITE_URL`, matching the AS metadata `issuer`.
- **Offline verification is first-class.** Better Auth's own resource-side verifier (`verifyJwsAccessToken`) does `jwtVerify` against a local JWKS set (`createLocalJWKSet`) with required `issuer` and `audience` options, cache + kid-miss refresh ([core verify.ts](https://github.com/better-auth/better-auth/blob/main/packages/core/src/oauth2/verify.ts)) — the same model `backend/src/auth.rs` already implements with `jsonwebtoken`.
- **Refresh/revocation.** "This implementation currently issues a new refresh token for every refresh request" (rotation); refresh tokens are only issued when `offline_access` is in the granted scopes ([token.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/token.ts): a refresh token requires `offline_access`); `POST /oauth2/revoke` (RFC 7009) revokes a refresh token and its child access tokens ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider)). Because access tokens are stateless JWTs, revocation is visible to the Review Engine only at expiry (or via `/oauth2/introspect`) — keep `accessTokenExpiresIn` short. Claude refreshes reactively on 401 and proactively up to 5 min before expiry (prior research, fixed constraint).
- **Static JWKS for the Review Engine.** The component supports exporting a static JWKS (`npx convex run auth:rotateKeys | npx convex env set JWKS`) and building the public JWKS document (`createPublicJwks`) ([auth-config.ts](https://github.com/get-convex/better-auth/blob/main/src/auth-config.ts)); the Review Engine's `JWT_JWKS` env can hold the public output of `GET /api/auth/convex/jwks`. Rotation then requires re-provisioning the Review Engine — or `auth.rs` grows a fetched-JWKS mode mirroring Better Auth's cache-and-refresh-on-unknown-kid behavior.

**Concrete `backend/src/auth.rs` deltas:** (a) audience: replace the single `CONVEX_AUDIENCE = "convex"` with a configured audience set — `"convex"` for browser session JWTs and the exact Coach MCP resource URL for MCP access tokens (or split validators per endpoint class); (b) optionally read the `scope` claim to enforce the Coach scope on MCP-originated calls; (c) issuer, RS256, exp/iss/aud/sub requirements, and `sub`-as-Player-ID all survive unchanged — but stored Player IDs keyed to the old `userId|sessionId` composite subject must be migrated. Convex-side: `auth.config.ts` switches to `getAuthConfigProvider()` (customJwt). If Convex functions must also accept MCP access tokens as identities, `auth.config.ts` can carry a second `customJwt` provider with `applicationID` = the resource URL — the component requires exactly one provider with `applicationID: "convex"` but tolerates others ([convex plugin source](https://github.com/get-convex/better-auth/blob/main/src/plugins/convex/index.ts), `parseAuthConfig`).

### Scopes

Defaults are `["openid", "profile", "email", "offline_access"]`; the `scopes` option replaces/extends the list, `advertisedMetadata.scopes_supported` controls what RFC 8414 metadata advertises, and DCR clients get `clientRegistrationDefaultScopes`/`clientRegistrationAllowedScopes` ([oauth.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/oauth.ts), [types/index.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/types/index.ts)). A Coach scope (e.g. `coach:review`) is just a custom entry in `scopes` plus `scopes_supported` in the Coach MCP PRM. Hosts choose scopes per prior research: Claude takes the 401 `scope` parameter, else `scopes_supported` (adding `offline_access` when advertised — required for refresh tokens here); ChatGPT echoes PRM `resource` and scopes. The consent page receives the requested `scope` in the signed query from `/oauth2/authorize` and the granted scopes surface in the JWT `scope` claim and in `oauthConsent` rows ([authorize.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/authorize.ts), [token.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/token.ts)).

| PRM (RFC 9728)                         | `https://<coach-mcp-host>/.well-known/oauth-protected-resource[/path]`, served by the Coach MCP server, `authorization_servers: ["https://<slug>.convex.site"]` (single entry — Claude only reads the first)       |
| Login + consent pages                  | the Vite app (`SITE_URL`; localhost in dev — acceptable because the _user's browser_ performs the authorize redirect, while both AS and MCP endpoints are public HTTPS for Claude's `160.79.104.0/21` egress)      |

The root-route requirement follows from `registerRoutes` mounting only `pathPrefix /api/auth/` plus a root `/.well-known/openid-configuration` redirect aimed at the **convex plugin's** OIDC metadata ([create-client.ts](https://github.com/get-convex/better-auth/blob/main/src/client/create-client.ts)) — that document describes the Convex session-JWT issuer, not the OAuth endpoints. The prototype adds root `http.route`s for `/.well-known/oauth-authorization-server` (and optionally an OAuth-aware `openid-configuration`) that invoke the same Better Auth HTTP action; the plugin's `onRequest` metadata matcher operates on the request pathname, so a root-path invocation should hit it (verify — the older mcp plugin docs likewise instruct adding an explicit root route because "some client may fail to parse the `WWW-Authenticate` header and default to `/.well-known/oauth-protected-resource`", [mcp docs source](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/plugins/mcp.mdx)).

### Registration paths

- **DCR (RFC 7591):** `allowDynamicClientRegistration: true` enables `POST /oauth2/register` and puts `registration_endpoint` in metadata; `allowUnauthenticatedClientRegistration: true` additionally allows public/anonymous registration and is what flips `"none"` into `token_endpoint_auth_methods_supported` ([metadata.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/metadata.ts)). The docs warn: "If you use `allowUnauthenticatedClientRegistration`, you must ensure that your API Server is a confidential client itself"; registration is rate-limited (5 req/min default) ([oauth-provider docs](https://www.better-auth.com/docs/plugins/oauth-provider)). Both ChatGPT and Claude need unauthenticated DCR (they register anonymously).
- **CIMD:** not available in better-auth 1.6.x. Feature request [#7184](https://github.com/better-auth/better-auth/issues/7184) closed as completed via [PR #9159](https://github.com/better-auth/better-auth/pull/9159) ("Adds `@better-auth/cimd` for unauthenticated client discovery via Client ID Metadata Documents… ships in v1.7.0-beta.1" per the closing comment). The component pins `better-auth <1.7.0`, so the dev deployment cannot advertise `client_id_metadata_document_supported` yet. Consequence per the fixed host contract: Claude selects DCR (its documented fallback); ChatGPT "prioritizes CIMD when available" with DCR optional — so ChatGPT must take the DCR path here (its exact behavior absent CIMD is an open risk).
- **Pre-registered clients (dev option):** clients are `oauthClient` rows (fields include `redirectUris`, `tokenEndpointAuthMethod`, `public`, `requirePKCE`, `skipConsent`) creatable server-side; `cachedTrustedClients: Set<string>` short-circuits DB validation for known client ids ([schema.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/schema.ts), [types/index.ts](https://github.com/better-auth/better-auth/blob/main/packages/oauth-provider/src/types/index.ts)). Claude's custom-connector UI accepts a pasted client id/secret (prior research), so a pre-registered confidential client with redirect URI `https://claude.ai/api/mcp/auth_callback` is a viable DCR-free dev fallback.

### Test accounts

Better Auth email/password: `requireEmailVerification` defaults to `false`, sign-up enabled unless `disableSignUp`, password 8–128 chars ([email-password docs](https://better-auth.com/docs/authentication/email-password)) — so headless test Players are not blocked by verification unless ChenChess enables it. The component's own example gates verification on an env flag (`requireEmailVerification: process.env.IS_TEST !== "true"`, [examples/react/convex/auth.ts](https://github.com/get-convex/better-auth/blob/main/examples/react/convex/auth.ts)). Seeding: `auth.api.signUpEmail()` server-side ([email-password docs](https://better-auth.com/docs/authentication/email-password)) — on Convex, inside an internal action via `createAuth(ctx).api` since "auth.api methods need to run in a Convex function" ([Convex integration docs](https://better-auth.com/docs/integrations/convex)). Two seeded Players (e.g. `player-a@test`, `player-b@test`) each complete their own authorize→consent flow per host connection; no shared state beyond the component tables.

## Constraints on the prototype

1. **Stack:** `@convex-dev/better-auth@0.12.5` (Local Install layout, `convex/betterAuth/`), `better-auth@~1.6.23`, `@better-auth/oauth-provider@1.6.23`; drop `@convex-dev/auth` + `@auth/core`; `convex/auth.config.ts` → `getAuthConfigProvider()`.
2. **AS config:** `oauthProvider({ loginPage, consentPage, scopes: ["openid","profile","email","offline_access","coach:review"], validAudiences: [COACH_MCP_URL], allowDynamicClientRegistration: true, allowUnauthenticatedClientRegistration: true, accessTokenExpiresIn: <short> })` alongside `convex({ authConfig })` and `crossDomain({ siteUrl })`; add root well-known route(s) in `convex/http.ts`; silence/clear the issuer-metadata init warnings only after the root URL verifiably serves RFC 8414 JSON with `code_challenge_methods_supported: ["S256"]` and `"none"` in `token_endpoint_auth_methods_supported`.
3. **Resource side:** Coach MCP server serves PRM at its own origin (`resource` = exact connector URL, `authorization_servers` = `[CONVEX_SITE_URL]`, `scopes_supported` incl. `offline_access` + Coach scope) and returns 401 + `WWW-Authenticate: Bearer resource_metadata="…"` on unauthenticated calls — replicating `mcpHandler` semantics in Rust.
4. **Rust `auth.rs`:** parameterize audience (Coach MCP resource URL and/or `"convex"` per route class), keep RS256/iss/exp/sub requirements, source `JWT_JWKS` from `/api/auth/convex/jwks` output (accept re-provision on key rotation, or add JWKS fetch with kid-miss refresh), optionally enforce `scope`.
5. **Frontend:** implement `/oauth/login` and `/oauth/consent` routes in the Vite app rendering the signed-query params and POSTing to `/oauth2/consent` via the Better Auth client (crossDomain cookies to `*.convex.site`).
6. **Keep every OAuth endpoint under Claude's 10 s deadline** — all endpoints are single Convex HTTP actions + component DB calls, no LLM/engine work on this path.

**Prototype acceptance checklist:**

- [ ] `GET https://<slug>.convex.site/.well-known/oauth-authorization-server` returns RFC 8414 metadata (issuer = `CONVEX_SITE_URL`, S256, `"none"` advertised, registration + revocation endpoints present).
- [ ] `GET https://<coach-mcp>/.well-known/oauth-protected-resource` returns PRM; unauthenticated `POST /mcp` returns 401 + `WWW-Authenticate: Bearer resource_metadata=…`.
- [ ] Claude custom connector completes DCR → authorize → login → consent → `https://claude.ai/api/mcp/auth_callback` → form-urlencoded token exchange with `resource`, and lists Coach tools.
- [ ] ChatGPT connector completes the same via DCR to `https://chatgpt.com/connector/oauth/{callback_id}`, PRM `resource` echoed into token `aud`.
- [ ] Issued access token is an RS256 JWT: `iss = CONVEX_SITE_URL`, `aud` = Coach MCP URL, `sub` = Better Auth user id, `scope` includes the Coach scope; validates offline in `backend/src/auth.rs` against static JWKS.
- [ ] The same Player's browser session JWT (`aud: "convex"`) validates in Convex (`ctx.auth.getUserIdentity()`) and yields the same `sub`.
- [ ] Refresh: token response includes rotated refresh token (requires `offline_access`); Claude survives access-token expiry (reactive 401 + proactive refresh) without re-consent.
- [ ] Revocation: `POST /oauth2/revoke` invalidates the refresh token; host is forced back through authorize after access-token expiry.
- [ ] Two seeded test Players hold concurrent connections from both hosts; tokens never cross Player boundaries (`sub` isolation verified in Review Engine logs).

## Open questions / UNCONFIRMED

- **Does `oauthProvider()` coexist with the component's `convex()` plugin?** `convex()` internally instantiates its own `jwt` (issuer/aud/adapter overrides) and a metadata-only `oidcProvider`; whether `@better-auth/oauth-provider`'s `getJwtPlugin` resolves that instance cleanly (shared RS256 keys, no duplicate-plugin conflict, no double `/jwks`) is undocumented and untested — first thing the prototype must prove.
- **Root well-known forwarding on Convex:** whether invoking the Better Auth HTTP action from a root-path `http.route` triggers the plugin's `onRequest` metadata matcher (vs needing a redirect, and whether ChatGPT/Claude follow redirects on metadata fetches).
- **`/.well-known/openid-configuration` collision:** `registerRoutes` claims the root path for the convex plugin's session-JWT metadata; whether hosts ever fall back to it (and get non-OAuth metadata) needs a check.
- **ChatGPT's registration behavior without CIMD** (docs say DCR "optional", CIMD "prioritized"; the DCR-only path is asserted but unverified against a live connector).
- **Cross-origin consent:** consent/login pages on `SITE_URL` with Better Auth cookies on `*.convex.site` via `crossDomain` — the authorize→login→consent→authorize round-trip in a third-party-cookie-restricted browser is unverified.
- **Password-hash portability** from `@convex-dev/auth` (Lucia Scrypt) to Better Auth scrypt (parameter/format compatibility unverified; dev can recreate accounts instead).
- **Component 1.7 timeline:** when `@convex-dev/better-auth` lifts the `<1.7.0` pin, `@better-auth/cimd` becomes available and the registration story upgrades to CIMD for both hosts.
- **Old-subject data migration:** extent of backend/Convex data keyed by the current `userId|sessionId` composite `sub` that must be re-keyed to stable Better Auth user ids.
- **`resource` parameter emission:** both hosts are required by MCP to send RFC 8707 `resource` (prior research); if a host omits it on the token request, `@better-auth/oauth-provider` falls back to a non-resource (opaque-audience) token — behavior to observe live.
